# 03. 질의 이해·라우팅·직접 기능

## 목표와 필요성

모든 질문을 하나의 RAG 경로로 보내면 느리고 오류 유형도 늘어난다. 현재의 직접 기능 우선 구조는 **프로젝트에 매우 필요**하다. 반면 LLM 질의 분석은 모든 요청에 필요한 것이 아니라 복합·후속·모호 질문에만 필요한 보조 기능이다.

주요 구현은 [rag_service.py](../../api/rag_service.py), [query_analysis.py](../../src/services/query_analysis.py), [query_expansion.py](../../src/utils/query_expansion.py)에 있다.

## 현재 기능 경로

| 우선순위 | 기능 | 현재 판단 | 개선 방향 |
|---:|---|---|---|
| 1 | 위기/자해 대응 | 필수 | 민감 로그 보존 정책과 전문기관 정보 최신성 점검 |
| 2 | WISE 캠퍼스 범위 차단 | 현재 서비스 범위상 필요 | 거절 사유와 서울캠퍼스 대안 안내 일관화 |
| 3 | 과목 추천 | 필요 | 추천 근거·필터 조건·빈 결과 설명 강화 |
| 4 | 시맨틱 캐시 | 기본 OFF가 적절 | 정합성과 revision 무효화 후 제한 도입 |
| 5 | 스몰토크 | 필요하나 최소화 | 검색 없이 빠르게 종료하고 비용 제한 |
| 6 | 미공개 미래 정보 | 필수 안전장치 | “없음”과 “아직 발표 전”을 구분 |
| 7 | 학사일정·급식 직접 응답 | 매우 필요 | freshness gate와 구조화 응답 계약 강화 |
| 8 | LLM 질의 분석 | 조건부 필요 | 단순 질의에서는 건너뛰기 |
| 9 | 일반 라우팅·검색 | 필수 | 원인별 fallback과 route confidence 추가 |

최근 실트래픽 표본에서 질의 분석은 실행 요청당 평균 약 2.65초로, 답변 생성 전에 발생하는 가장 큰 지연이다. route별 fallback은 notices 58건 중 20건, staff 18건 중 7건으로 특히 높았다. 반면 schedule 43건과 meals 11건은 fallback이 없어서 결정적 경로의 효용이 확인된다.

2026-09-23에는 명시적 학번의 졸업·교양 기준 질문도 단일 `rules` route로 확정되면 질의 분석 LLM을 우회하도록 했다. 후속 질문, 시의성·변경·신청 공지, 복합 질문은 이 우회 대상이 아니다. 구조형 fixture 45건의 결정적 route는 점검했지만 운영 질문의 route 정확도는 사람 판정이 필요하다.

## 발견된 위험

- 전체 테스트에서 질의 분석 관련 3건이 실패했다. 격리 실행과 전체 실행 결과가 달라지는 전역 lazy singleton/monkeypatch 오염 가능성이 높다.
- 스트리밍과 비스트리밍 경로가 각각 긴 orchestration을 구현해 기능 추가 시 우선순위와 로깅이 달라질 수 있다.
- LLM 분석 결과가 실패할 때 휴리스틱 fallback은 있지만, 분석 실패율과 최종 route 정확도를 함께 보는 지표가 없다.
- `unknown` route가 최근 표본에서 55건이다. fallback은 낮지만 “검색 불필요 직접 응답”과 “의도 분류 실패”가 섞여 있을 수 있다.
- 위기 질의와 사용자 질문 원문이 관측 DB에 얼마나 오래 남는지 별도 정책이 없다. 민감 질문은 최소 수집·단기 보존·접근 제한이 필요하다.

## 기능 개선 작업

### P0

- 질의 분석 클라이언트를 request-scoped dependency 또는 명시적 factory로 만들고 테스트 fixture에서 singleton을 초기화한다.
- `_get_analysis_chain`과 공개 주입 지점을 하나로 통일하고 전체 실행, 개별 실행, 무작위 순서, 반복 실행을 모두 통과시킨다.
- 각 경로가 공통 `QueryPlan`을 반환하게 한다. 최소 필드는 `intent`, `routes`, `filters`, `direct_handler`, `confidence`, `reason`, `time_sensitivity`다.

### P1

- 아래 조건에서는 LLM 질의 분석을 건너뛴다.
  - 날짜와 대상이 명확한 일정/급식 질문
  - 과목코드, 전화번호, 규정명, 게시판명이 명시된 단일 의도 질문
  - 위기·스몰토크·지원하지 않는 캠퍼스처럼 결정 규칙이 명확한 질문
- 다음 조건에만 분석 LLM을 사용한다.
  - 이전 대화를 참조하는 후속 질문
  - 여러 데이터셋을 결합해야 하는 질문
  - 동일 표현이 학사일정/공지/규정에서 충돌하는 질문
  - 필수 슬롯이 빠져 clarification 판단이 필요한 질문
- notices에 장학, 수강신청, 기숙사, 국제교류 등 도메인 별칭을 보강하고 게시일/마감일/현재 유효 의도를 분리한다.
- staff에는 학과명 변형, 단과대명, 부서 약칭, 담당 업무 표현 사전을 정본 엔터티에서 생성한다.
- “알 수 없음”, “아직 발표 전”, “서비스 범위 밖”, “데이터가 오래됨”, “검색 결과 없음”을 서로 다른 사용자 응답과 fallback reason으로 제공한다.
- 과목 추천은 추천 조건과 제외 조건을 구조화해 출처와 함께 보여주고, 사용자가 학년/전공/관심사를 수정해 재실행할 수 있게 한다.

### P2

- 작은 규칙/분류 모델과 LLM analyzer를 오프라인에서 비교하고, route 정확도와 지연을 함께 기준으로 cascade를 구성한다.
- 직접 기능 결과를 텍스트가 아닌 typed payload로 반환해 웹, 앱, 알림에서 동일 데이터를 재사용한다.

## 성능 개선 작업

- 대화 이력 로딩과 독립적인 정적 의도 감지는 병렬 수행한다.
- analyzer timeout을 전체 요청 timeout과 분리하고, 초과 시 결정적 planner로 즉시 전환한다.
- 정규화된 질문과 대화 문맥 hash 기준으로 짧은 분석 캐시를 두되 개인정보와 시간 민감 query는 제외한다.
- 단순 질의에서 분석 호출률을 줄이는 것이 1차 목표다. 모델 교체는 그다음이다.

## 완료 조건

- 단일 의도 골든셋 route accuracy 95% 이상, 복합/후속 질의 90% 이상을 달성한다.
- 전체 실트래픽의 질의 분석 호출률과 skip 사유가 측정된다.
- 품질 비열화 없이 분석 단계 p95를 1초 이하로 낮추거나, 전체 요청의 70% 이상에서 호출을 생략한다.
- notices/staff fallback을 원인별로 분류하고 검증 세트에서 절대 5%p 이상 낮춘다.
- 민감 질의의 원문 저장, 접근권한, 보존기간, 삭제 절차가 문서와 코드에서 일치한다.
